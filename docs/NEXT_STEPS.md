# 下一阶段实施规划：真实 Agent、可替换场景与可恢复执行

2026-11-17 · M2 实施计划 · 状态：待执行

2026-11-17 讨论补充：近期先明确任务、评分和基线，跑通点胶单场景的真实 Agent 与最小恢复闭环，再用灌装检验兼容性。工作包定义继续保留；当前交付顺序见 [知识库 M2 验收](knowledge/m2-plan.md)，研究依据与决策见 [知识库](knowledge/README.md)。

本计划将完整 Proposal 的 M2 拆成可验收工作包，并将 M3 的最小恢复能力提前。它定义后续工作，不表示这些能力已经实现。已有验证以 [STATUS.md](STATUS.md) 为准；完整路线见 [ROADMAP.md](ROADMAP.md)。

## 1 当前起点与本阶段目标

v0.1 已具备点胶、灌装两种有状态软件产线，合成 PNG 的像素测量，动作约束、固定复核、SQLite 事件/工单/证据以及离线对照。已有十个固定任务和十三个测试方法通过。真实模型仅做协议 mock；FUXA/MQTT 尚未实测；进程中断后尚不能恢复世界继续执行；Neuroptica 只有独立未训练数值功能检查。

本阶段应交付三项核心证据：一条真实模型完成的点胶处置轨迹、一套不修改运行核心即可切换的灌装适配器、一次进程中断后不重复执行已接受动作的恢复测试。工作台与光学任务继续推进，但不替代这三项验收。

## 3 WP1：真实模型闭环与必要性对照

先保持动作白名单、版本/有效期检查、维护前暂停和固定复核不变。模型使用公开观测、手册和工具返回值，不能读取隐藏故障、操作者注入参数或评分真值。记录 role、工具参数、回执、frame_id、状态版本、模型/提示词版本、实际耗时，以及可取得的 token 用量和费用；拿不到的费用标记 unknown，不填零。

比较三个方案：现有离线规则对照、单 Agent、诊断/规划/验证多角色。三者使用相同输入、工具集、动作约束和终态判据；单 Agent 使用多角色工具权限的合理并集，不能故意削弱基线。比较时固定总工具预算和总体模型用量上限，报告真实消耗；若达不到相同模型用量条件，单列差异。固定复核开销对三种方案一致计入。

已有十个固定任务用于功能回归。正常条件的 recovered 是状态检查，不能算维修成功；持续故障的正确移交不能算恢复。开发期间可使用这些任务调试，但不要把它们称为隐藏测试或用它们推断领域成功率。

在独立保留任务上增加噪声、观测过期、工具超时、无效维修与未见条件。先验证这些扰动能影响环境或工具，再冻结任务、种子、阈值和评分器。随机种子数量与模型重复次数应在运行前确定，不能看见结果后挑选。

报告：正确恢复、正确移交、正确停止、失败、误报恢复、错误动作、重复状态变更、工具次数、耗时和费用。按故障类型和产线分别展示；保留失败轨迹。多角色是否有收益由结果决定，不以角色数量作为成效。

## 4 WP2：将内置场景改为适配契约

首版仍有场景相关渲染/测量分支。目标是将这些分支移入适配器，使核心运行器只处理稳定对象。

| 接口职责 | 场景适配器提供 | 运行核心负责 |
| --- | --- | --- |
| 场景声明 | scene_id、版本、测量任务、手册、允许动作、能力 | 注册、发现、选择和版本记录 |
| 世界状态 | 初始化、序列化、恢复、状态变更 | 任务关联、并发和检查点时机 |
| 观测与感知 | 渲染/采集、测量、来源、质量、单位 | 时间与版本关联、证据保存 |
| 动作语义 | 参数模式、状态前提、设备适用性、执行/查询 | 权限、TTL、幂等账本、预算与审计 |
| 复核 | 场景恢复条件和未解决条件 | 强制采集新证据、判定终态、工单关联 |

继续使用 Observation、Measurement、ActionRequest、Receipt、Verification 等对象。ActionRequest 至少包含设备/场景身份、action_id、参数、expected_version 和 expires_at；Receipt 关联前后版本与执行状态。拒绝“未知能力”时返回明确错误，不能默默使用不适用的默认动作。

验收时用同一入口切换点胶与灌装，检查运行核心无新增工艺条件分支。新增产线仍需实现渲染、测量、动作因果和阈值；这不等于任意设备只改配置即可接入。

## 5 WP3：队列与恢复能力提前进入本阶段

先支持单服务、单设备队列：queued → running → verifying → recovered / handed_off / stopped / failed。区分“暂停任务”和“暂停设备”；人工停止、预算结束和运行异常分别保存原因。查询接口不应等待整个处置结束才返回。

动作账本持久化 action_id、参数摘要、请求版本、前置条件、执行状态、回执和关联观测。相同 ID 同参数返回已知结果；同 ID 不同参数拒绝。对请求超时或回执丢失，先查询动作状态，再决定如何恢复。真实设备不能保证查询时，将结果标记为 unknown 并停止或移交，不假装实现了跨系统 exactly-once。

模拟器检查点保存世界状态、版本、事件进度和未决动作。隐藏故障可以存在于受控模拟检查点，但不得进入 Agent 上下文或公开证据。真实设备恢复依赖设备侧状态与查询能力，不能直接套用软件世界快照。

必要注入点：执行前中断、状态变更后回执保存前中断、回执保存后任务进度保存前中断、相同请求重放、进程重启。验收必须证明任务可续接或有明确的不可恢复原因，且不会重复产生已确认的维修状态变更。多设备、跨进程租约和人员/备件预约保留在完整 M3。

## 6 WP4：FUXA / MQTT 的真实联通

先读后写。输出可导入的点胶与灌装 FUXA 工程，连接实际 broker，展示设备运行、供压、测量质量、测量值、事件阶段、工具活动和终态，并能打开相应 PNG 与工具轨迹。

当前桥接仅发布最近完成事件，不能冒充实时遥测。下一版需让执行中状态可读，并为消息提供时间、状态版本和事件身份；明确 topic、单位、数据类型、retained 消息、重复及过期处理。检查 broker 断开/重连、旧 retained 消息、重复消息、图像无效时的 null 值、事件与设备身份错配。展示告警确认不等于设备恢复。

部署步骤以固定 FUXA 提交为依据，记录实际主机、依赖和启动结果；没有部署证据的部分继续标记未验证。具体接入背景见 [FUXA_INTEGRATION.md](FUXA_INTEGRATION.md)。

## 7 WP5：从光学功能检查走向任务实验

先选一个足够小且可重复的任务，例如基于 ROI 特征判断胶条质量。冻结特征、归一化、幅度编码、可映射变换、强度读出和数字后处理；在训练/校准与保留数据之间划清边界。

Neuroptica 与 NumPy 参考执行同一变换和读出。当前 numpy_identity fallback 不代表同一任务的等价回退，后续应提供同任务数字参考，或明确报告后端不可用。扫描相位偏差、噪声等参数时记录假设和数值范围，不把缺乏依据的扰动称为真实硬件模型。

报告任务质量、参考差异、扰动敏感性、回退触发和实际软件耗时。仿真耗时不等于实体芯片延迟；本阶段不承诺真实速度、功耗或商业优势。只有任务验证通过后，才考虑纳入 Agent 决策主链。
